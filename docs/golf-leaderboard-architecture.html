GGC Outdoor League — Leaderboard Architecture

How a Google Sheet + Apps Script web app back the leaderboard, and how data flows to the app and back.

Overview

The "GGC Outdoor League" leaderboard has no conventional backend server. A single Google Sheet is the database, and a Google Apps Script web app (appscript/Code.gs) deployed at a stable /exec URL is the only API in front of it. The Apps Script does not compute any scoring — net score, plus-minus, monthly points, ranks, and best-2-of-N round selection all live in sheet formulas. The script only reads cells via SpreadsheetApp and reshapes rows into JSON. The frontend (geosef/) is a static React SPA hosted on GitHub Pages that fetches those JSON blobs and renders them.

Data out: read path

doGet(e) is the single GET entry point. It routes on ?action= to a handler and serializes the result with ContentService as JSON. Live actions: leaderboard (default), monthly&month=April, scoringLog, handicapIndex, courses, courseInfo, getPrefs.

Each read handler follows the same shape:

  1. Check Apps Script CacheService (server-side script cache) for a key matching the action. TTLs vary by data volatility: leaderboard 15 min, monthly 30 min, scoringLog 15 min, handicap index 60 min, courses/courseInfo 60 min.
  2. On a miss, SpreadsheetApp.openById(SPREADSHEET_ID).getSheetByName(...) reads the cell values (getValues() / a column-capped getRange()).
  3. Map rows to plain JSON objects (e.g. { rank, name, points, events, isTied } for the leaderboard). Ranks, points, and plus-minus are read straight from sheet cells — the script only re-derives the isTied flag and a fallback rank.
  4. Cache the JSON (cache.put(...)) and return it.

There are two caching tiers:

  • Server-side: the CacheService step above, shared across all clients.
  • Client-side: a module-level sessionCache object in geosef/src/golf-cache.ts. It lives outside React, so it survives component unmount/remount for the whole browser session. Each fetch in GolfLeaderboard.tsx checks sessionCache first and only hits the network on a miss.

Key client optimization: only the two raw sheets — scoringLog and handicapIndex — are fetched once into sessionCache. Every per-player detail view (round history, monthly R1/R2 best rounds, handicap trend) is pure client-side computation off those cached blobs (see getMonthlyR1R2, tagCountingRounds, the expandedRounds filter in GolfLeaderboard.tsx). There are no per-player network calls.

URL resolution (config.ts + vite.config.ts)

APPS_SCRIPT_URL is resolved at build time:

  • Dev (import.meta.env.DEV): '/apps-script-proxy'. Apps Script blocks localhost CORS, so vite.config.ts proxies that path to the real /exec URL (changeOrigin, followRedirects, rewrite /apps-script-proxy → /exec).
  • Prod: the baked-in __APPS_SCRIPT_PROD_URL__ constant, which vite.config.ts injects via define, built from the deployment ID read from appscript/deployment-id.txt (or VITE_APPS_SCRIPT_DEPLOYMENT).

Data in: write paths

There are two distinct, unrelated write paths into the sheet:

1. Score submission — bypasses Apps Script entirely

Players submit rounds through a native Google Form (SUBMIT_SCORES_URL in GolfLayout.tsx, linked from the slide-in menu). Form responses land directly in the Scoring Log 2026 tab. Apps Script is not involved on the write side at all; it later just reads that tab for ?action=scoringLog. Sheet formulas then compute net score, plus-minus, monthly counts, and feed the monthly/total points sheets. Majors (The Open, Captains Cup) are entered manually by admins, not via the form.

2. User favorites — POST through Apps Script

The app writes favorites by POSTing JSON to /exec:

  • geosef/src/services/userPrefs.ts setPrefs() POSTs { action: 'setPrefs', token, favoritePlayers, favoriteCourses }.
  • doPost(e) parses the body and routes action: 'setPrefs' to setPrefsHandler, which verifies the token, then upserts a row keyed by email in the User Preferences tab (matching row updated in place, otherwise appendRow; the sheet is created with headers if missing).
  • useUserPrefs.ts drives the UI: it applies the toggle optimistically (updates state + localStorage cache immediately), fires setPrefs, and rolls back on failure. Reads go through getPrefs (a GET ?action=getPrefs&token=...).

setPrefs is currently the only POST action handled.

Auth (favorites only)

Auth gates only the favorites read/write — all leaderboard/scoring data is public.

  • Client (AuthContext.tsx): Google Identity Services (loaded from accounts.google.com/gsi/client) issues a JWT ID token on sign-in. It is decoded client-side for display (email/name/picture) and stored in localStorage (authToken) plus AuthContext. The token is sent on getPrefs (query param) and setPrefs (POST body).
  • Server (verifyTokenDetailed in Code.gs): calls Google's oauth2.googleapis.com/tokeninfo endpoint, then checks email_verified, the audience (payload.aud === OAUTH_CLIENT_ID, only if that script property is set), and roster membership — the email must exist in the League Roster 2026 tab's email column (index 4 / column E). Only roster members can read or write prefs; failures return { error: 'Unauthorized', reason, status: 403 }.

Gotchas / non-obvious bits

  • Errors come back as HTTP 200. Apps Script returns { error, reason } in the JSON body with a 200 status. Clients must inspect the parsed JSON, not the HTTP status (userPrefs.ts does exactly this).
  • POST uses Content-Type: text/plain to dodge a CORS preflight on the cross-origin Apps Script request.
  • CacheService has a ~100KB-per-entry limit. The scoringLog (and courses/courseInfo/handicapIndex) cache.put calls are wrapped in try/catch, so an oversized scoringLog is simply served uncached rather than erroring.
  • Wide sheets are column-capped. Handicap Index Log reads are capped at 252 columns and Playing Handicaps at 110 (Math.min(getLastColumn(), N)) — never getDataRange() these pivot tables.
  • Static SPA on GitHub Pages. No server-side rendering; everything client-side after the initial static load.
  • Manifest gotcha (from project CLAUDE.md): clasp push --force overwrites appsscript.json on Google's side. The webapp block (executeAs/access) must be preserved or /exec 404s for everyone, including local dev (which proxies to the same URL).
